## 기본 브랜치를 master에서 main으로 변경

- 앞서 `master`를 기본 브랜치로 올렸으나, 사용자의 원래 의도는 "`main`으로 바꿔서 거기에 올리는 것"이었다. 요청을 문자 그대로 해석한 결과라 다시 정리했다.
- `git branch -m master main` → `git push -u origin main` → GitHub 기본 브랜치를 `main`으로 변경 → 원격 `master` 삭제. 커밋 이력은 그대로 유지했다.
- 함께 만든 전역 슬래시 명령어 `/gh-push`의 기본 브랜치도 `main`으로 맞췄다. 이제 `master` 브랜치를 발견하면 `main`으로 자동 변경한다.
  - 관련 파일: `~/.claude/commands/gh-push.md`, `~/.claude/scripts/gh-push.sh`, `~/Desktop/gh-push-명령어.txt`

## Kafka / Redis / RabbitMQ 로컬 컨테이너 구성

- 요청: LTS 버전의 Kafka, Redis, RabbitMQ를 Docker 컨테이너로 실행할 수 있는 `docker-compose.yaml`과 실행 스크립트.
- 버전 선정: Docker Hub 태그와 각 프로젝트 지원 주기 문서를 조회했다.
  - Kafka는 LTS 지정 자체가 없어 최신 안정 버전 `4.3.1`을 썼다. 4.x는 ZooKeeper가 없어 KRaft 단일 노드(broker+controller 겸용)로 구성했다.
  - Redis 오픈소스도 LTS 표기가 없지만 8.2가 지원 종료 2030-09-01로 명시된 라인이라 `8.2.9-alpine`을 골랐다.
  - RabbitMQ는 4.2가 공식 LTS 시리즈라 `4.2.9-management-alpine`을 썼다. 다만 커뮤니티 지원은 2026-07-31에 끝났고 이후는 상용 지원 대상이다. LTS 요구를 우선해 4.2로 두되 `.env`의 `RABBITMQ_VERSION`으로 4.3(커뮤니티 지원 2026-11-30까지)으로 바꿀 수 있게 했다.
- 리스너 분리: Kafka는 호스트용(`localhost:9092`)과 컨테이너용(`kafka:19092`) 리스너를 따로 광고하도록 했다. 백엔드를 호스트에서 실행하든 컨테이너로 옮기든 그대로 쓸 수 있다.
- 데이터 유지 문제 수정: 처음에 Kafka 볼륨을 `/var/lib/kafka`에 붙였는데, 이미지가 `/var/lib/kafka/data`를 `VOLUME`으로 선언하고 있어 더 깊은 경로의 익명 볼륨이 우선하면서 컨테이너를 다시 만들 때마다 데이터가 사라졌다. 마운트 경로를 `/var/lib/kafka/data`로 정확히 맞춰 해결했고, 재기동 후 토픽·키·vhost가 모두 남는 것을 확인했다.
- 스크립트 수정 사항 두 가지
  - macOS 기본 bash 3.2에서는 `set -u` 상태의 빈 배열 전개가 오류라 `${arr[@]+"${arr[@]}"}` 형태로 바꿨다.
  - 포트 점유 검사가 이미 떠 있는 자기 컨테이너까지 잡아서 `up`을 두 번 실행할 수 없었다. 프로젝트 컨테이너가 쓰는 포트는 검사에서 제외해 멱등하게 만들었다.
- 검증: `make infra-up` → 세 서비스 healthy, `make infra-smoke` → Kafka 토픽 생성·발행·소비, Redis set/get, RabbitMQ 진단 모두 통과. 호스트에서 9092/6379/5672/15672 접속과 Kafka 브로커 API 응답도 확인했다. `down` 후 재기동 시 데이터 유지도 확인했다.
- 관련 파일: `docker-compose.yaml`, `scripts/infra.sh`, `.env.example`, `Makefile`, `README.md`, `PROGRESS.md`

## 명령 래퍼(`scripts/`, `Makefile`) 제거

- 사용자 판단으로 `scripts/` 폴더 전체와 `Makefile`을 삭제했다. 래퍼 없이 `npm`, `./gradlew`, `docker compose`를 직접 쓰기로 했다.
- 삭제 범위를 먼저 확인했다. `scripts/infra.sh`만 지우는 선택지도 제시했지만, `scripts/harness.py`(= `make doctor/setup/dev/verify/smoke`의 실체)까지 포함해 전부 지우는 쪽을 택했다.
- 이에 따라 사라진 기능과 대체 명령을 README에 다시 정리했다.
  - `make setup` → `npm ci`, `./gradlew classes testClasses`
  - `make dev` → 터미널 두 개에서 `./gradlew bootRun`, `npm run dev` (한 번에 띄우고 함께 종료하던 동작은 없어짐)
  - `make verify` → `npm run lint && npm run build`, `./gradlew check bootJar`
  - `make smoke` → 개발 서버를 띄운 상태에서 `curl http://localhost:8080/api/health`, `curl http://localhost:5173/api/health`
  - `make infra-*` → `docker compose up -d --wait` / `ps` / `logs -f <서비스>` / `down` / `down -v`
- 함께 없어진 것 두 가지를 기록해 둔다.
  - `doctor`의 Node 24·JDK 21 강제 확인이 사라져 버전 확인은 수동(`node --version`, `java -version`)이다.
  - harness가 `GRADLE_USER_HOME`·`npm_config_cache`를 `.cache/`로 묶어 두던 것이 사라져 이제 각 도구의 기본 캐시 위치를 쓴다.
- `docker compose up -d --wait`가 헬스체크 통과까지 대기하므로 infra.sh의 대기 로직은 대체 가능했다. 포트 선점 검사와 왕복 스모크 테스트는 대체 없이 없어졌다.
- 관련 파일: `README.md`, `AGENTS.md`, `PROGRESS.md`, 삭제: `scripts/harness.py`, `scripts/infra.sh`, `Makefile`

## `COMMANDS.md` 추가

- 자주 쓰는 명령을 한 줄 설명으로 모아달라는 요청. 처음에는 설치·검증·브로커 CLI까지 74줄로 만들었으나 "그냥 실행/종료만" 이라는 피드백을 받고 실행·종료 쌍만 남겨 대폭 줄였다.
- 이어서 Docker는 개별 서비스 실행·종료도 필요하다고 해서 추가했다. 개별 종료는 `down`이 아니라 `stop`을 썼다. `down`은 서비스를 지정해도 네트워크까지 걷어내서 개별 제어에는 맞지 않는다.
- 중간에 개별 항목이 사라진 적이 있다. 사용자가 이전 버전을 기준으로 파일을 직접 편집·저장하면서(`프런트엔드` → `프론트엔드`) 덮어써진 것이라, 사용자 표기를 유지한 채 개별 항목만 다시 넣었다.
- 검증: `docker compose stop kafka`로 Kafka만 내려가고 Redis·RabbitMQ가 유지되는 것, `docker compose up -d kafka`로 다시 뜨는 것을 확인했다.
- 관련 파일: `COMMANDS.md`, `README.md`(구성 목록에 한 줄 참조 추가)
